最初に、小さな機能をプロジェクトに追加しました。大きな変更には、より確実なプロセスが必要です。GitHub Copilot app は組織の既存のワークフローに沿って動作し、適切な方法で必要な機能を開発できます。このレッスンから数回にわたり、issue から新機能を実装し、コードの妥当性と機能の動作を確認して、プロジェクトにマージするまでの一般的なエージェント型開発の流れを実践します。

> [!NOTE]
> 機能開発を進める間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは主な概念に集中するため手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub issue から新しいエージェント セッションを開始します。
- **Plan** モードで要件を決めます。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動で検証します。

この機能開発を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能 PR を作成します。

## シナリオ

Tailspin Toys のカタログが増え、ユーザーがカテゴリやパブリッシャーでゲームを絞り込めるようにする必要があります。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードで決定し、範囲を限定して Autopilot に実装を任せます。

## 背景

AI コーディング エージェントを開発フローに取り入れても、基本は変わりません。むしろ、より重要になります。多くの開発者は次のような流れで作業します。

1. 必要な作業の詳細が記載された issue を開きます。
2. 実装する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードのレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや Organization によって異なりますが、多くの場合は上記の流れに近いものです。

この標準的な方法を守ることで、AI が生成したコードが要件を満たし、手書きのコードと同じレビューを受けるようにできます。

## セッション モード

**セッション モード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプト フィールド下部のドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、次に進む前に入力を待ちます。
- **Plan**: エージェントは計画を作成します。エージェントが実行する前に、計画をレビューして承認します。
- **Autopilot**: エージェントは完全に自律して作業し、入力を待たずにコードを書き、テストを実行して改善を繰り返します。

Plan モードで始めて計画をレビューし、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリ フォルダーを選択し、リポジトリ上部のナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる issue です。新しい issue を作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モード選択から **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## 絞り込み機能を計画する

計画を立てると、Copilot がコードを書く前にアプローチをレビューできます。issue から開始したため、Copilot は機能リクエストをすでにコンテキストとして把握しています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を issue の受け入れ条件と照らし合わせます。カテゴリとパブリッシャーによる絞り込み、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確認します。複数カテゴリを組み合わせる方法や、一致するゲームがない場合の動作など、不明確な点について話し合います。

計画には、プロジェクトで既存のツールを使った lint、ユニットテスト、E2E テスト、型チェックを含める必要があります。範囲は絞り込み機能の実装とテストに限定し、品質ワークフローを終えてから PR を作成します。計画を承認する前に修正を依頼し、後で検証するために issue の URL と合意した補足事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan** または使用中のバージョンで同等のオプションを選択します。承認しただけでモードが切り替わると思い込まず、アクティブなモードを確認してください。モード表示が **Autopilot** になっていることを確かめます。

Copilot は実装に取りかかります。合意した計画に沿ってコードを生成し、テストを実行しながら反復します。

> [!NOTE]
> 承認すると実装がすぐ始まる場合があります。先に計画をレビューしてください。依存関係が不足している、またはポートが競合していると Copilot が報告した場合は、チェック完了とみなす前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、他のコードと同じようにマージ前にレビューします。コードを確認し、サイトを実行して問題がないことを確かめましょう。

1. **Changes** を開き、絞り込み機能の実装とテストを確認します。
2. 複数カテゴリやパブリッシャーの組み合わせも含め、結果を issue と承認済みの補足事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることも確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、影響するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカル サーバーを再利用することがあります。テスト対象が前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認しましょう。前と同じようにアプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザー キャンバスで開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選択し、結果が一致することを確認します。フィルターを解除してからパブリッシャーを選択し、その結果も確認します。
4. カテゴリとパブリッシャーのフィルターを組み合わせ、issue と承認した計画に結果が合っていることを確認します。複数カテゴリがサポートされている場合は、合意した組み合わせの動作も検証します。
5. 一致するゲームがない組み合わせを試し、空の状態を確認します。フィルターをクリアまたはリセットし、一覧全体に戻ることも確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンのためにセッションを保持する

絞り込み機能の PR は、まだ作成またはマージしないでください。レッスン 4 から 8 まで同じセッション、worktree、ブランチを使います。次はカスタム指示を絞り込み機能のコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR を作成してマージします。開発サーバーを停止した後はセッションをアイドル状態にしておき、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

さまざまなエージェント モードを使って機能を開発し、レビューしました。

- GitHub issue から新しいエージェント セッションを開始しました。
- **Plan** モードで要件を決めました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザー キャンバスで機能を手動で検証しました。
